# @yukibana/project-schema

Every version of `yukibana.json` and `yukibana.release.json`, and nothing else: one strict zod schema per version,
the migrations from each version to the next, and the JSON Schema of each version. Only `zod` is a dependency and
nothing imports from Node, so the IDE's frontend, the Worker and the website can use it as well as the CLI.

- `parseProjectFile(text)` reads a `yukibana.json` at the version it names, strict (every field required, no other
  allowed), and migrates it to the latest. It returns the latest `ProjectFile` and the file as written, or a
  `ReadError`: not JSON, not an object, no `version`, a newer version than this package reads (with both numbers), a
  version that never existed, or every field problem. `describe(name, error)` words it.
- `parseReleaseFile(text)` does the same for `yukibana.release.json`, the project and release a starter is.
- `exact<B>()` and `Migration<A, B>` (`src/exact.ts`): a migration returns `Checked<B>`, which only `exact` makes,
  and `exact` does not compile when its argument has a key `B` lacks, at any depth, spreads included.
- `format(name, schemas, steps)` (`src/versions.ts`) is the chain: version `N` is `schemas[N - 1]` and the compiler
  checks that each step goes from one version to the next.

## A new version

1. Add `src/v<N>.ts`, a copy of the latest changed as needed, with its own `$schema` literal
   (`https://yukibana.dev/schema/yukibana/v<N>.json`) and `version: z.literal(<N>)`.
2. Append it to `PROJECT_FILE_VERSIONS` in `src/migrations.ts` and write its step,
   `Migration<ProjectFileV<N-1>, ProjectFileV<N>>`, returning through `exact`. Point `ProjectFile`, `AnyProjectFile`,
   `SCHEMA_URL` and `KINDS` in `src/project-file.ts` at it.
3. `pnpm --filter @yukibana/project-schema schemas` writes `schemas/yukibana/v<N>.json`.

## Released versions

`released.json` lists, per file, the versions that have been released. A released version's schema file in
`schemas/` is never rewritten: `tests/json-schema.test.ts` compares it byte for byte and fails on any change, while
an unreleased version's file is regenerated by `pnpm --filter @yukibana/project-schema schemas`.

## Where the schemas are served

The website (`Yukibana-Ed/website`, https://yukibana.dev) serves them. Its build fetches `schemas/index.json` and every
file it lists from one pinned commit of this repository and copies them to `https://yukibana.dev/schema/`, so `schemas/yukibana/v1.json` is
`https://yukibana.dev/schema/yukibana/v1.json`, the `$schema` a version 1 file names. A released version is served as
immutable; an unreleased one with a short cache. Its CI deploys it; nobody deploys by hand. A new version, or a
version's release, reaches the site when the website's pin is moved to a commit of `main` that has it.

`pnpm --filter @yukibana/project-schema typecheck` also compiles a consumer of the built declarations with
TypeScript 6 (`scripts/ts6.ts`), which `cloud/web`'s `svelte-check` uses.
